## 2024-05-24 - Information Disclosure via Raw Exceptions in API Responses
**Vulnerability:** The application was exposing raw python exceptions (`str(e)`) directly to users via JSON responses on the `/health` and `/search` endpoints. In `/health`, component failure stack traces or internal model loading errors were sent in the 'error' field. In `/search`, generic exceptions were caught and their message sent back via `_error_response`.
**Learning:** It's a common anti-pattern to pass exception strings directly into API responses for debugging purposes during development, which then mistakenly leak into production. This can expose sensitive internal path details, database versions, or framework mechanics to potential attackers.
**Prevention:** Catch specific exceptions rather than broad `Exception`. Always sanitize error messages that cross the trust boundary (to clients) by returning generic error messages (e.g., "Internal component failure" or "An internal error occurred"). Log the detailed raw exception (`str(e)`) securely on the server-side instead for internal debugging.
